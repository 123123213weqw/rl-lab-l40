# GRPO step-50 到底改变了什么：能力实测

日期：2026-10-26。对象：`rl-grpo8b-baseline-20261016` 的 base 与 `exported-step50-final`。

## 结论

**能力没有变强，也没有变弱。变的只有「输出格式合规」这一件事。**

## 证据链

### 1. 原口径（严格 `#### N`）

| | base | trained | 差 | McNemar |
|---|---|---|---|---|
| GSM8K 官方测试 n=1319 | 73.77% | 93.40% | **+19.64pp** | p=1.5e-59 |

这是真实存在的差异，但它测的是格式。

### 2. 同一批预测，换成免格式口径

| 口径 | base | trained | 差 | 95% CI | 变对/变错 | p |
|---|---|---|---|---|---|---|
| strict（原） | 73.77% | 93.40% | +19.64pp | [+17.36, +22.06] | 279 / 20 | 1.5e-59 |
| last_num（取末位数字） | 93.18% | 93.48% | +0.30pp | [-0.76, +1.44] | 30 / 26 | 0.689 |
| contains（答案出现过） | 94.54% | 94.77% | +0.23pp | [-0.83, +1.29] | 27 / 24 | 0.780 |

免格式后差异不显著。

### 3. 一个正则就能替代这次 GRPO

```
base strict                     73.77%
base + 正则取最后一个数字        93.18%   (+19.41pp)
trained（GRPO 50 步）           93.40%   (+19.64pp)
```

正则覆盖 GRPO 增益的 **98.8%**；GRPO 相对 base+正则的净增量 **+0.23pp**。

### 4. 换问法重新生成（不给 `####` 指令，n=1319）

| | base | trained | 差 | 95% CI | 变对/变错 | p |
|---|---|---|---|---|---|---|
| GSM8K 中性问法 | 92.57% | 93.18% | +0.61pp | [-0.38, +1.67] | 29 / 21 | 0.322 |

模型没有依赖被训练出的格式；脱离该指令后两边同样水平。

### 5. 域外能力（ARC-Challenge，n=1172）

| | base | trained |
|---|---|---|
| ARC-Challenge | 90.19% (1057/1172) | 90.19% (1057/1172) |

- 逐条判断一致 1170/1172，变对 1 / 变错 1，McNemar p=1
- 输出文本逐字节相同 958/1172 (81.7%)

通用科学推理能力**零变化**，没有被损伤。

## 关键推论：原 baseline 的 73.77% 是被格式口径压低的结果

Qwen3-8B（已 post-train，thinking 关闭）在 GSM8K 测试集的真实水平约 **93–94.5%**。
原评测要求回答末尾恰好一行 `#### <number>`，而该模型默认不这么写，
于是 285/1319 条「算对了但没按格式收尾」被判 0 分：

- base 格式不合规的 346 条中，正确答案出现在文本任意位置的有 **274 条**
- 两臂都格式合规的 953 条中，contains 口径 **两臂都是 100%**

所以 `base 73.77%` 不是模型能力，是格式协议不匹配。

## 为什么奖励设计必然导致这个结果

- 格式违规 → 0 分，单点梯度最大 → GRPO 先吃掉它
- 训练日志 `critic/score/mean`：step1 0.695 → step3 0.922 → 之后 47 步在 0.90–0.98 波动
- **格式信号 3 步饱和**，剩余 47 步主要把 KL 从 0.0004 漂到 0.05

## 缺的对照臂

要证明 GRPO 在这里有边际价值，需要「只修格式、不做 RL」的臂：

- 格式 SFT（几百条 `#### N` 样本）或 few-shot 把格式压上去
- 在同一 1319 条上评测
- 若它同样达到 93–94%，则本次 GRPO 的边际贡献为零

## 复现

```bash
cd $RL_LAB
PATH=$RL_LAB/.tools/bin:$PATH \
VLLM_USE_FLASHINFER_SAMPLER=0 CUDA_VISIBLE_DEVICES=1 \
$VLLM_PY 04_capability_eval.py \
  --model <checkpoint> --out results/<arm>.json --n-arc 0 --n-gsm 0 --max-tokens 512
```

环境注意（踩过的坑）：
- 该机器 `/usr/local/cuda` 的 nvcc 是 **11.8**，flashinfer JIT 需要 `--compress-mode=size`（12.8+），
  必须设 `VLLM_USE_FLASHINFER_SAMPLER=0`
- vLLM 的 JIT 需要 `ninja`，系统没有 → 已装在 `$RL_LAB/.tools/bin`
- 数据由 `dump_eval_sets.py` 预导出到 `rl-lab/data/`，避免改你的 vllm 环境

## 局限

- 单一训练种子，无多 seed 复现
- ARC 用「首个 A–D 字母」抽取，绝对分数可能有偏差；但它对两臂施加相同口径，
  配对比较有效
- GSM8K 测试集虽未参与训练，但已被用于最终基准，不能排除预训练污染
